## How to run work here

- One docket run per phase, named `docket-cost-workflow-pN`. The supervisor acts
  as planner, orchestrator, verifier and reviewer; each implementor is a separate
  session.
- An implementor editing `skills/docket/bin/docket` must drive lifecycle commands
  from the installed copy at `~/.agents/skills/docket/bin/docket`, or it is using
  the file it is rewriting.
- `docket dispatch` records a binding and launches nothing. Sessions are started
  by hand: `herdr tab create`, `herdr agent start <name> --kind opencode --pane
  <id> -- --auto`, then `docket session --register` and `docket dispatch` with the
  herdr `terminal_id` as the session, then `herdr agent prompt`.
- Read the live model and effort from the agent's status line, never from
  configuration. `~/.codex/config.toml` said `low` while the pane showed `high`.
- Run the suite with `FORCE_COLOR` unset, and capture full output to a file.
  Piping through `tail` masks the exit code, and this shell sets `FORCE_COLOR=3`,
  which for five phases made a real product bug look like a flaky test.
- Never put backticks in a `--reason` argument. The shell expands them and the
  decision artifact is immutable, so the mangled text cannot be corrected.

## What review here actually means

Every task in these ten phases was reviewed by reproducing its claims against
the built code, not by reading its report. That caught things reports did not
say, and twice caught the report being right where a first reading of the patch
suggested otherwise. Two specific habits are worth keeping:

- A removal count of zero in a patch does not mean no existing test was touched.
  An inserted argument changes a test's behavior while removing no line.
- When a task's state has moved on, a spot check against it can mislead. An
  approved task renders as stage `review`, so a prompt check against it refuses
  for reasons that have nothing to do with the change under review.

## Where the defects have actually been

Useful for aiming the next audit. Every defect found so far fell into one of:

- A feature that passes its own tests but cannot be operated through the real
  command surface.
- Two code paths that must agree forever with nothing forcing them to.
- A state where no role receives an actionable event, or receives one that
  misdescribes the state.
- A gate satisfied by something other than the evidence it claims to require.
- A command that advertises an option it then refuses, or reports success for
  something nothing will honour.

# Docket improvement requests

Issues hit while orchestrating `pybot-live-temporal-parity-v2` in split topology
across two nested Git repositories plus a parity worktree.

`.docket/improvement.md` already records the planner's list from an earlier run.
Items there are not repeated here.
Where this run produced new evidence for one of those items, it is noted as an
extension rather than restated.

## 1. `docket diff` is silently inert outside a single Git root

**Severity: high. This is the most consequential issue in the run.**

The run directory lives at the repository *parent*, which is not itself a Git
repository, while the actual code lives in the nested `pybot/` and `services/`
repositories and in a Git worktree outside both.
Docket recorded `git_root: ""` in every task snapshot, so `docket diff <run> <task>`
returned `no worktree changes since assignment` for all seven tasks, even when a
task had added over a thousand lines.

The skill states that the task-local diff is review truth alongside the report.
For this entire run that truth was unavailable, and nothing said so.
I reviewed every change by running `git status` and `git diff` directly in the
relevant checkout instead.

Requests:

- Fail loudly at `docket assign` when no Git root can be resolved, rather than
  writing an empty `git_root` and degrading silently at review time.
- Report `diff unavailable: no git root` instead of `no worktree changes`.
  Those two statements mean opposite things to a reviewer, and the current wording
  actively misleads.
- Support multiple roots per run: resolve each scope path to its own repository and
  produce a per-root diff.

## 1b. `docket decide` destroys the approved report and discards the approval reason

**Severity: high. This silently deleted review evidence across an entire run.**

Approving a report overwrites `Txx-report-NN.mdx` with an 18 to 24 line verdict
stub containing only `## Verdict` and `## Notes`. The submitted report, with its
limitations, acceptance mapping, verification output, derivation tables, and
adversarial battery, is gone. The matching `Txx-decision-NN.mdx` is also written as
a stub, and the text passed to `--reason` does not appear in it: every approval in
this run shows `## Notes` followed by `none`.

Measured across this run's seven tasks:

- Every final, approved report is a stub. `T01-report-02`, `T02-report-03`,
  `T03-report-01`, `T04-report-03`, `T06-report-01` and `T07-report-02` are all 24
  lines with 2 sections. The waived `T05-report-02` is 28 lines.
- Every superseded round survives intact: `T07-report-01` is 204 lines,
  `T05-report-01` is 308, `T01-report-01` is 228.
- `--changes` decisions survive fully: `T07-decision-01` is 87 lines with its
  numbered corrections. Only the approval path loses content.

So the damage is worst exactly where the evidence matters most. For a task approved
on a later round, the previous round's report preserves most of the substance. For a
task approved on its first round there is no earlier copy, so the entire report is
unrecoverable. In this run that destroyed `T03-report-01` and `T06-report-01`
outright.

This also defeats the skill's own model. The playbook states that the submitted
report and the task-local diff are the review truth. After approval, neither exists:
the diff gate was already inert per item 1, and the report has been replaced by its
own verdict.

Requests:

- Never write decision content into the report file. The report and the decision are
  separate artifacts and the decision file already exists for this purpose.
- Persist the `--reason` text into the decision file. Discarding it silently means an
  approval carries no rationale, which is the one thing a later reader needs most.
- If a stub is wanted for quick status reads, add a `verdict:` field to the report
  frontmatter rather than replacing the body.
- Treat this as a regression test: approve a report, then assert the body is
  unchanged and the decision contains the reason.

## 1c. There is no way to check for a pending event without consuming it

Checking whether a wake event is queued consumes it. `docket watch` claims events
under a file lock, and it has no peek or dry-run mode, so the only way to answer
"did my submission queue a planner wake" is to take the wake.

Worse, the role guard does not prevent this across sessions. Running
`DOCKET_ROLE=planner docket watch --role planner` from the orchestrator session
claims the planner's event, which is exactly the cross-role consumption the
`DOCKET_ROLE` design is meant to prevent. The variable gates whether the hook is
inert, not who is allowed to claim what.

I did this three times in this run while confirming that aggregate reports had
reached the planner. Each time the planner still picked the work up, so nothing was
lost, but that was luck rather than design: the report status is visible through
`docket status --role planner`, so a planner that polls status recovers, while a
planner relying solely on its watcher would sit idle.

Requests:

- Add a non-destructive `docket watch --peek` or `docket events --list` that
  reports pending events without claiming them.
- Refuse to claim events for a role when the claiming process is not that role's
  watcher, or at minimum warn loudly.
- Make a consumed-but-unhandled event recoverable, so an accidental claim can be
  requeued rather than silently dropped.

## 2. No support for multi-repository or worktree-based runs

Related to item 1 but broader.
Scope paths in this run spanned `pybot/`, `services/`, and
`.worktrees/services-parity-pybot-live-temporal`, which is a worktree of `services`
rooted outside it.
Docket's snapshot, diff, and preflight model assumes one working tree.

Requests:

- Let a run declare multiple roots, and resolve scope paths against them.
- Follow `git worktree` links so work done in a worktree is visible to the diff
  gate.
- Record the branch and head of each root in the snapshot, so a reviewer can tell
  which checkout a change landed in.

## 3. A waiver is terminal, with no reopen path

When the planner reviewed the aggregate report, it rejected a waiver I had granted
and asked for the task to be completed and reviewed normally.
That turned out to be impossible.

- `docket decide <run> T05 --changes` refuses: *"has status: waived - only
  submitted or blocked reports are reviewable"*.
- `docket assign <run> T05` refuses: *"already has a report; use `docket decide` to
  open a new round"*.
- The implementor playbook forbids editing `status:` by hand.

So a waived task is permanently closed, even to the reviewer who asked for it to be
reopened.
The only path was to open a new task id carrying the original's completion, which
breaks the one-to-one mapping between the plan's task table and the run's tasks and
makes the final report harder to read.

Requests:

- Add `docket reopen <run> <owner>`, or accept `docket decide --changes` on a waived
  report, so a planner-rejected waiver can be undone.
- Alternatively let a new task declare `supersedes: T05`, so the substitution is
  first class rather than a naming convention in prose.

## 4. The aggregate report has no snapshot or diff of its own

The planner asked for reviewable aggregate diffs and noted there is no `orch`
snapshot to produce them from.
`docket assign <run> orch` creates the report but records no baseline, so there is
no mechanical way to answer "what did this whole run change".

Requests:

- Snapshot every root at the first task assignment of a run, and let
  `docket diff <run> orch` produce the cumulative diff.
- Or add `docket bundle <run>` to emit per-root patch artifacts plus base and head
  metadata under the run directory, which is what the planner asked me to build by
  hand.

## 5. Model switching cannot be driven reliably, and `--continue` silently wins

Extends `improvement.md` item 4, with new specifics.

The orchestrator playbook says to switch an OpenCode model in place with `Ctrl+X`
then `M`, preserving the session.
In practice, driving that picker through `herdr agent send-keys` was not reliable:
a stray `m` landed in the search field, prompt text did not consistently reach the
filter, and arrow navigation scrolled past the Recent list.

The documented fallback also failed in a way worth recording: relaunching with
`opencode --auto --continue --model <other>` restored the session's *stored* model
and ignored the flag.
Verifying the displayed label caught it, exactly as the playbook warns, but that
means there is no reliable scripted path to change model while keeping a session.

Requests:

- Provide `docket switch-model <run> <owner> --model X` that performs the switch
  through the harness API rather than through terminal keystrokes, then verifies and
  records the active label.
- Document that `--continue` takes precedence over `--model` in OpenCode, so the
  combination cannot be used to move a resumed session to a different model.

## 6. `docket set-model` reports a false mismatch for unpinned launches

When an implementor is launched as plain `opencode --auto` with no pinned model,
there is no meaningful `requested_model`.
Recording the verified label then emits
`WARNING: requested model '...' is not active`, which reads as a problem when the
launch was deliberately unpinned.

Request: allow `--requested none` or an explicit unpinned marker, and suppress the
mismatch warning in that case.

## 7. Submission accepts a report whose checkboxes contradict its own prose

Extends `improvement.md` item 8, with a second pattern.

That item covers an acceptance claim contradicted by the report's notes.
This run produced a sharper variant: reports that tick every acceptance box while a
`## Limitations` section directly above states that several proofs are unit level
only, or that a comparison is "echo-by-construction".
The implementor was honest in prose and optimistic in checkboxes, and `docket
submit` accepted both.

Request: when a report contains a limitations or caveats section, require each
checked criterion to be absent from it, or require an explicit
`PARTIAL: <gap>` annotation on the criterion line.
Cheap to implement as a text-level gate and it would have saved two review rounds
here.

## 8. Silent stall when an implementor runs out of capacity

Extends `improvement.md` item 10.

Twice an implementor hit a provider rate limit mid task, went idle with its report
still in `draft`, and produced no signal at all.
Lifecycle state showed `done`, which is indistinguishable from finished work, and
the run looked healthy for an hour.
Only reading the pane revealed `Free limit reached`.

I now instruct implementors to file a `docket handoff` before stopping, and I watch
for the rate-limit string directly rather than for the absence of a submission, but
neither should be the orchestrator's job.

Requests:

- Emit an orchestrator event when a dispatched task goes idle with an unsubmitted
  report past a threshold.
- Distinguish `done: submitted` from `idle: nothing submitted` in status, rather
  than showing both as a task in `draft`.

## What worked well, and should not be traded away

- `model_history` on the task and report captured every mid-task model transition
  faithfully, including a switch away and back. That record was the only reliable
  account of what produced which work.
- The two-phase `decide --changes` flow, where the first call opens the draft and
  the second applies it, made it natural to write specific numbered corrections
  rather than a vague verdict.
- Batched review wakes worked exactly as documented: one wake per completed batch,
  with blockers and checkpoints arriving immediately.
- Requiring the implementor to own the discovery capsule kept repository knowledge
  in the cheap harness. I never needed to hand an implementor a code map.

## Retrospective after a completed run

`pybot-live-temporal-parity-v2` ran to completion in split topology: a planner, a
Claude Opus 5 orchestrator, and a single OpenCode implementor, across twelve tasks,
four aggregate report rounds, two nested Git repositories and a parity worktree.
The items above were all hit during that run. This section records what the
experience says about the skill's shape, as opposed to individual defects.

### What the design got right

- Implementor-owned discovery capsules kept repository knowledge in the cheap
  harness. Over twelve tasks the orchestrator never had to hand an implementor a
  code map, and scope claims stayed accurate and disjoint.
- The two-phase `decide --changes` flow, where the first call opens a draft and the
  second applies it, pushes a reviewer toward specific numbered corrections instead
  of a verdict. That shaped the review quality more than any other single feature.
- Batched review wakes behaved exactly as documented, with blockers and checkpoints
  arriving immediately and ordinary submissions batched.
- `model_history` on the task and report was the only reliable account of which
  model produced which work, across a mid-task switch away and back.
- The split cost boundary held. The planner read four aggregate reports and never
  saw task-level traffic, and it caught the three deepest defects of the run
  precisely because it was reading a summary with fresh eyes.

### The structural weakness

Every enforcement point that matters is prose in a playbook, not a gate in the CLI.
Docket validates that report sections exist and that acceptance criteria match the
task, which is real, but it cannot tell the difference between:

- a criterion satisfied and a criterion ticked;
- a comparison that compares system output and one that compares a value the test
  supplied;
- a gate that evaluated the supplied input and one that evaluated a committed
  fixture;
- a fixture corrected toward the reference and a fixture bent toward the
  implementation.

Each of those four shipped at least once in this run and was caught by a human-style
read, not by tooling. Two were caught only at the third layer. The skill's own
principle is that the submitted report and the task-local diff are the review truth,
and in this run the diff gate was inert for every task (item 1) and the report was
destroyed on approval (item 1b), so for stretches of the run neither source of truth
existed.

If one change were possible, it would be to make submission refuse a report whose
ticked criteria are contradicted by its own limitations section. That is a text-level
check, it costs nothing, and it would have saved several rounds here.

### Where the orchestrator's cost actually went

Not to dispatch or lifecycle, which the CLI handles. It went to re-running every
claim, building independent adversarial inputs, and tracing cited line numbers in
the reference implementation. That work is not delegable to the current tooling and
it is the reason the topology worked at all. A cheap preliminary reviewer, as
`improvement.md` item 9 proposes, would have absorbed much of it.

### Smaller frictions worth fixing together

- No `orch` snapshot, so aggregate diffs had to be produced by hand (item 4).
- A waiver is terminal, so a planner-rejected waiver forced a new task id and broke
  the plan's task-table mapping (item 3).
- No non-destructive way to check for a pending event, and a cross-role peek claims
  another role's wake (item 1c).
- Model switching cannot be driven reliably, and `--continue` silently overrides
  `--model` (item 5).
- An implementor that loses provider capacity goes idle with a draft report and no
  checkpoint, indistinguishable from finished work (item 8). This happened three
  times and instruction alone did not prevent it.
